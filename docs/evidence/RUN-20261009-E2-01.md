## Workload and controls

Each fixture reads its initial claim status, lodges a claim with durable asynchronous receipt, retries the same intended claim, answers an independently seeded follow-up question, attempts an ungranted employment change, revokes authority and attempts another submission. Every request has a request ID and ground-truth intent ID; claim retry shares its original intent. Forbidden/revoked attempts are separate from the three legitimate intents.

B uses registered opaque representative identity plus an independently citizen-approved, scoped, expiring, revocable **HMRC-owned** relationship. C uses the real Delegate identity/consent/check implementation. Both use identical HMRC HTTP routes, business handlers, eligibility, idempotency, durable queue, worker budget and default throughput settings from one production build. HMRC and its worker restart before each block; fresh subjects isolate persisted business state. The database is seeded once for the isolated job, not reset between blocks; unique subjects and new per-arm credentials/grants isolate workload state.

Human sign-in, handoff and approval are replaced with direct synthetic citizen fixtures in **both** arms. Human time, assistance, drop-off, comprehension and support are **unmeasured/null**, not zero. The API checks whether the representative asserted approval of the answer; that is not independently verified real citizen agreement.

Each block has 45 passing assertions. These are correlated checks within five citizen fixtures, not 45 independent participants. Both arms handle all fixed legitimate tasks and prevent all tested unauthorised effects. The workload found **no incremental outcome advantage for Delegate** over this safe service-local control. C has higher observed median request latency in both paired blocks. This is descriptive and conflates authority runtime/storage, startup effects and architecture; it does **not** isolate a causal Delegate overhead estimate.

Raw technical-work proxies are request counts and ServiceEvent cost classes. B's event table also includes approval/revocation/receipt/outcome rows whereas C's exported ActivityEvent table contains authority checks; total event counts are **not comparable cost denominators**. No financial savings or real-world failure probability is inferred. No confidence intervals: tiny purposive synthetic workload, not a population sample.

## Interpretation and next action

The result supports bounded software feasibility: an authorised service-local representative can use the same robust HMRC API without Delegate, while both paths enforce the tested scope and revocation controls. HMRC owns duplicate prevention and queue integrity in both arms. This is useful counterevidence to any assertion that Delegate uniquely supplies those outcomes.

It does not demonstrate that citizen control is equally usable, that independent cross-service authority has no value, or that Delegate is cheaper/more expensive in production. Human intervention and consent friction remain unmeasured; there are no real agents, taxpayers, field outcomes or national capacity findings. Consequential transaction approval, provider handoff, disputes and multi-service reuse need separate matched extensions.

Next: independent review of preserved raw records; publish/review the genuine consent/handoff effort and cross-service reuse comparison before making an incremental-benefit decision.
